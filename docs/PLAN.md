# Спецификация и план

Цель: воспроизводимый FastAPI/PostgreSQL сервис генерации с финансовыми
изменениями exactly-once внутри БД, устойчивой очередью отправки, двумя
персистентными фейковыми провайдерами, watchdog и проверками реальной конкурентности.
Пользователь пополняет баланс подписанным webhook, создаёт задачу, читает её историю.
Публичная авторизация пользователей и реальные генеративные API вне тестового задания.

## Выбранная архитектура

PostgreSQL хранит каталог, пользователей, ledger, задачи, попытки, outbox,
идемпотентные задания провайдеров и настройки сценариев. API запускается в четырёх
процессах; отдельный worker читает outbox и запускает watchdog. Дополнительные
экземпляры worker допустимы. Redis/Celery не нужны: транзакция с outbox закрывает
разрыв между фиксацией задачи и HTTP. DB leases и fencing token защищают от старых
ответов отправителя. Сетевые запросы выполняются вне транзакций.

Инварианты:

1. Баланс меняет только INSERT в ledger через триггер PostgreSQL; ledger append-only.
2. UNIQUE(payment_id), UNIQUE(task_id, kind); отрицательный баланс запрещён CHECK.
3. Все изменения состояния берут блокировки user → task → attempt → outbox.
4. Пользовательская блокировка охватывает проверку активных задач и списание.
5. Изменять задачу может лишь её текущая нетерминальная попытка.
6. Watchdog и webhook используют один переход; после timeout поздний результат игнорируется.
7. Одна логическая попытка имеет неизменный UUID, outbox и provider idempotency key.
8. Внешняя доставка at-least-once; дедупликация провайдером сохраняется в PostgreSQL.

Пограничные случаи: ответ потерян после приёма; падение до/после COMMIT; callback
раньше ответа POST; два callback; webhook одновременно с watchdog; исчерпание ног;
moderation исключает skip_on_moderation ноги на всей оставшейся цепочке; payload
немедленно останавливает цепочку. Считаем стартом timeout создание попытки: даже
неотправленная из-за недоступного worker попытка имеет конечный срок жизни.

## Этапы и проверки

1. `pyproject.toml`, `app/models.py`, `migrations/`: схема, ограничения, seed и триггеры.
   Проверка: `alembic upgrade head`, `alembic check`, rollback/upgrade на тестовой БД.
2. `app/service.py`, `app/api.py`: транзакции, HMAC, API и общие переходы.
   Проверка: pytest финансовых инвариантов и параллельных HTTP-запросов.
3. `app/worker.py`, `app/provider.py`: leases, fencing, HTTPX, durable fake providers.
   Проверка: повторная обработка, просроченный lease, потерянный ответ, timeout.
4. `tests/`, `scripts/`: настоящая PostgreSQL; детерминированные гонки без random sleep;
   smoke через четыре Uvicorn worker и реальные provider HTTP-сервисы.
5. Dockerfile/Compose, README, CI, аудит задания. `ruff check .`, `ruff format --check .`,
   `pytest`, полный smoke, `git diff --check`, проверка секретов/статуса Git.
6. Коммиты по фактическим этапам; публикация нового репозитория только если доступна
   авторизация и создание репозитория. Существующие remote не перезаписывать.

Выполнение последовательное, без субагентов. Риски: недоступный Docker/сеть;
проверять локальной PostgreSQL, явно отделять это от Docker-проверки. Развёртывание
не выполняется поверх существующей БД. Откат миграции разрушает данные и применяется
только к выделенной тестовой базе. Скачанные инструменты и секреты исключены из Git.
